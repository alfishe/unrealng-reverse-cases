## Planned ports

| OCP Video Pool | UKNC; possibly BK-0010 / BK-0011M and Soyuz-Neon | `games/<case>/docs/14-porting-to-uknc.md` |

The porting document follows AGENTS.md section 4.0 "By port target". What it must address for each target (the machine facts here are leads from memory; the document checks each one against the machine's documentation or an emulator before it relies on it):

| Target | What the document must address |
| --- | --- |
| UKNC (Elektronika MS-0511) | the PDP-11 central CPU (K1801VM2) and the peripheral CPU that owns the video and sound; the three-plane video memory in the peripheral CPU's space, written through its ports or by a peripheral-CPU program; the channels between the two CPUs; which work runs on which CPU, and how they sync per frame |
| BK-0010 / BK-0011M | the K1801VM1 at 3-4 MHz, no multiply; the 256x256 two-bit or 512x256 one-bit screen in main memory; the 32K or paged 128K budget; the beeper or AY add-on; the timer |
| Soyuz-Neon (PK-11/16) | the CPU: N1806VM2, the CMOS version of the K1801VM2, functionally equivalent (not the K1801VM3 this lead first said; Wikipedia "1801 series CPU" <https://en.wikipedia.org/wiki/1801_series_CPU> and Cyclowiki "Союз-Неон ПК-11/16" <https://cyclowiki.org/wiki/%D0%A1%D0%BE%D1%8E%D0%B7-%D0%9D%D0%B5%D0%BE%D0%BD_%D0%9F%D0%9A-11/16>, Video Pool doc 14.9), so the UKNC's VM2 timings apply; the clock to verify (Cyclowiki 8 MHz, Wikipedia 5 MHz nominal); 1-4 MB of RAM; its video modes and palette; what of the BK or UKNC plan carries over |

## For unreal-ng

- Chuckie Egg: the game's state after K frames depends on how they are split into `control_execution run_frames` calls (two faults, reproduced with probes): [docs/unreal-ng-run-frames-faults.md](docs/unreal-ng-run-frames-faults.md) (the probe scripts stay in the case's untracked `work/stage2/`).
- Tujad: a TTD session cannot record an RZX playback, and an RZX's inputs replayed from its saved state drift from the game within frames: the game is deterministic but timing-sensitive (EnergyTimer `$6366` counts interrupts, Random calls depend on passes) and the RZX frames are not one interrupt each (0.87 taken per frame), so whether unreal-ng's interrupt timing differs from the recording machine's is not shown (games/tujad/work/stage2/NOTES.md 3.6). The stage-1 walkthrough was cut into 59 checked pieces (games/tujad/WALKTHROUGH.md section 5).
- SimCity: `time_travel dump` of a long session (139 382 and 145 000 frames) fails with HTTP 409 "a write failed (disk full or device gone)" while about 900 GB are free and leaves a partial file (57.8 MB); the capture itself ran clean, so the fault is in the dump writer. Reproduced on the first try in stage 2; captures up to 96 503 frames dump fine, so the city recording was split into `city` and `city2` (games/simcity/work/stage1/NOTES.md, work/stage2/NOTES.md).
- Terramex: after a TZX `$2A` stop-the-tape block (the Quicksilva re-release, block 4 of `Terramex (Quicksilva).tzx`, on a 48K at ROM speed) `POST /tape/play` answers "Tape playback resumed (in place)" but the tape stays paused at that block, so the 48K path cannot load the last block (500 frames after the call the state is still paused at block 4). The same after an explicit `POST /tape/pause` on the original tape (no `$2A`) on a 48K: after `POST /tape/play` the state stays paused at block 4 for 15 000 frames and the loader ends on its "User pressed break-reload!" screen (a failed load of block 5). Probes and logs: games/terramex/work/stage2/probe_2a.py, p48/ (untracked).
- Switchblade: the analysis instance cannot load a TTD session recorded during `rzx_playback` (`analysis build` answers "not built: the analysis instance cannot load a session with the rzxplayback device"), so an RZX run gives no L1; reproduced 2026-11-12 on a 300-frame window (games/switchblade/tools/rec_rzx.py, work/stage2/rec/rzx-probe/record.json). The case replays the RZX's keys from SkoolKit snapshots every 2000 frames instead (tools/rzx_capture.py): 91 segments, 84 of them leave the RZX's state within the segment (median first divergence at frame 182), because the free-running main loop moves Hiro by passes and unreal-ng's 48K timing is not the recording machine's (work/stage2/NOTES.md).
- Deflektor: the original TZX (`orig/Deflektor.tzx.zip`) does not load: its last block is a turbo `$11` block with pause 0 and 3 bits in the last byte, and the player never gives the edge after its last pulse that the loader waits for (a real player does when the tape stops; the TZX spec advises a 1 ms pause for a last block with pause 0), so the load times out near frame 15 640 with IX = `$9DF0` and the loader jumps to `$0000`. The 10 Mega Games copy (the same three blocks, then a 16.5 s pause) loads; the case records from it (games/deflektor/work/stage1/NOTES.md). SkoolKit decodes the original exactly (games/deflektor/tools/tapesim.py).
