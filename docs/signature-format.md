# The signature base: the metadata format

`signatures/` holds the known pieces of ZX Spectrum programs: AY players, packers and their depackers, protections,
disk and tape loaders, ROM-call gadgets, fonts, and the modules of the finished cases. A scan of a new image against it
names the known pieces at once, with their base address and ready annotations for the case's `.ann`. The reverse then
starts from what is still unknown.

This document is the format: the folder tree, one entry's files, `sig.json` field by field, the match rules and the
index. The scripts that read it are `kit/sig_index.py` (builds and checks the index) and `kit/sig_scan.py` (scans an
image). Both are still to be written; this format is their specification.

## 1. The tree

The tree follows what a person looks for, not one flat list. An entry is a folder at a fixed depth:
`<domain>/<family>/<name>/<variant>/`. The folder path relative to `signatures/` is the entry's id, for example
`sound/ay-players/pro-tracker-3/vortex-1.0`.

```
signatures/
  README.md                       the tree and how to add an entry (points here)
  index.json                      generated by kit/sig_index.py, never edited by hand
  INDEX.md                        generated: every entry, by folder, one table row each
  sound/
    ay-players/                   pro-tracker-2/, pro-tracker-3/, sound-tracker/, asc-sound-master/, sqt/ ...
    beeper/                       beeper engines and tunes
    sfx/                          effect players (AY and beeper)
  packers/
    hrum/                         3.5/depacker, 3.5/setup ...
    hrust/                        1/depacker, 2/depacker ...
    laser-compact/, megalz/, zx7/ ...
  protection/
    ultraxor/                     1.2/layer, 1.2/reader ...
    tape/                         speedlock, alkatraz ...
  disk/
    tr-dos/                       ROM-gadget sector readers, catalogue readers, boot loaders
    loaders/                      third-party disk loaders
  tape/
    loaders/                      ROM LD-BYTES copies, turbo loaders
  system/
    interrupts/                   IM 2 table set-ups, interrupt wrappers
    input/                        keyboard scans, Kempston, redefine routines
    paging/                       128K and Pentagon page switchers
    print/                        text printers, number printers
  graphics/
    fonts/                        the ROM font and known fonts (data)
    screen/                       clears, copies, attribute fills, sprite blitters
    pictures/                     known title pictures (data)
  rom/
    48k/, 128k/, tr-dos-5.04t/ ...  ROM routine entry points, as `kind: rom` entries
  programs/
    games/<game>/<module>/        the modules of a finished case, by the case's module names
    demos/<demo>/<part>/          the parts of a finished demo case
  formats/
    music/                        pt2-module/, pt3-module/, stc-module/ ... (detectors, no bytes)
    graphics/                     scr/, hrust-stream/ ...
```

Rules for names:

- lower case, words joined by `-`, no spaces: `pro-tracker-3`, not `ProTracker3`;
- `<family>` is the program or the author's series; `<name>` is the program inside it or its version; `<variant>`
  separates builds of the same piece (`vortex-1.0`, `compiled-2.4`, `ane-1998`). An entry with no variant uses
  `main`;
- when the version is unknown, the variant names the first case it was found in (`seen-advanced-nether-earth`);
- the domains above are fixed; a new domain needs a row in this section. Families and names grow freely.

## 2. One entry

| File | Required | What |
| --- | --- | --- |
| `sig.json` | yes | the metadata (section 3) |
| `code.bin` or `data.bin` | for `code` and `data` entries | the reference bytes, as they lie in memory at the origin address |
| `detect.py` | for `format` entries | the detector (section 5) |
| `notes.md` | no | longer notes: the history of the piece, its variants, links |

The bytes come from the cases' originals and carry the same rights note as `games/<game>/orig/`
([README](../README.md#rights)).

## 3. sig.json

Numbers are decimal JSON numbers. Addresses are strings in the repository's notation, `"$C000"`. Offsets count from
the entry's first byte. A field marked "no" may be left out; an unknown value is `null`, never a guess.

### 3.1 Identity

| Field | Type | Required | What |
| --- | --- | --- | --- |
| `schema` | number | yes | the format version, `1` |
| `id` | string | yes | the folder path, `sound/ay-players/pro-tracker-3/vortex-1.0`; the index checks that they agree |
| `kind` | string | yes | `code`, `data`, `format` or `rom` (3.6) |
| `role` | string | yes | what the piece does, from the vocabulary in 3.7 |
| `name` | string | yes | a human name: `Pro Tracker 3 player, Vortex 1.0` |
| `authors` | list of strings | yes | as the program signs itself; `[]` when unsigned |
| `year` | number or null | yes | the first known year |
| `tags` | list of strings | yes | free search words, lower case: `ay`, `pt3`, `tr-dos`, `128k`, `self-modifying` |
| `summary` | string | yes | one sentence: what it is and how a program uses it |

### 3.2 The bytes

| Field | Type | Required | What |
| --- | --- | --- | --- |
| `bytes.file` | string | for `code`, `data` | `code.bin` or `data.bin` |
| `bytes.length` | number | for `code`, `data` | the file's length |
| `bytes.sha1` | string | for `code`, `data` | SHA-1 of the file |
| `bytes.masked_sha1` | string | for `code`, `data` | SHA-1 of the file with every masked byte (3.3) set to `$00` |
| `origin` | string | for `code`, `data` | the address the reference bytes run at, `"$C000"` |
| `relocatable` | boolean | for `code` | `true` when the piece is found at other addresses (its `rel16` words move with it) |

### 3.3 The mask

`mask` is a list of byte ranges that may differ from copy to copy. Every byte outside the mask must match exactly.
Each range is `{"offset": N, "length": N, "kind": K, "name": S}`. `name` is required for `ext16` and `data`, and
optional otherwise.

| `kind` | What it covers | How a match treats it |
| --- | --- | --- |
| `rel16` | a little-endian word that holds an address inside the piece (`JP`, `CALL`, `LD HL,nn` to its own code or data) | skipped in the byte compare. Every `rel16` must give the same delta, its value minus the reference value: that delta is the found piece's base shift |
| `ext16` | a word that holds an address outside the piece: the host program's buffer, tune or variables | skipped. The found value is reported under `name` (`tune`, `screen_buffer`) |
| `var8`, `var16` | settings and initial values that programs change: a speed, a self-modified operand's first value | skipped. The found value is reported |
| `data` | a block of data embedded in the code (a table a program may replace) | skipped. Reported as a range |

The mask is made once, by the person or agent that adds the entry, from the disassembly. ROM addresses (`CALL $3D13`)
and port numbers are not masked: they are the same in every copy and are the strongest evidence.

### 3.4 What a program sees

| Field | Type | Required | What |
| --- | --- | --- | --- |
| `entries` | list | for `code`, `rom` | the call points: `{"offset", "name", "in", "out", "clobbers", "summary"}`. `in` and `out` give registers and memory (`"HL = the tune"`), `clobbers` gives registers (`"AF BC DE HL IX"`, `"AF'"` when it swaps) |
| `labels` | list | no | names and comments inside the piece for the `.ann`: `{"offset", "name", "comment"}`; `name` may be empty for a comment only |
| `uses.ports` | list of strings | no | the ports it reads or writes: `"$FFFD w"`, `"$BFFD w"`, `"$1F r"` |
| `uses.memory` | list | no | the work areas it needs, inside or outside the piece: `{"offset" or "ext", "length", "name"}` |
| `uses.t_states` | object | no | `{"typical", "max", "witness"}`: the T-states a call takes, and the recording or script that measured it |
| `uses.needs` | list of strings | no | what the machine must have: `128k-paging`, `ay`, `tr-dos`, `im2`, `pentagon-timing` |

### 3.5 Where it comes from

| Field | Type | Required | What |
| --- | --- | --- | --- |
| `found_in` | list | yes | every copy known: `{"program", "case", "address", "bank", "delta", "match", "commit"}`. `case` is a path in this repository (`games/advanced-nether-earth`) or `null` for a program with no case. `match` is `exact` or `masked` (3.8). The first item is the reference copy whose bytes are in the entry |
| `source` | object | no | the annotated source of the reference copy: `{"case", "file", "label"}`, for example `{"case": "games/advanced-nether-earth", "file": "src/music/pt3-player.asm", "label": "Pt3Init"}` |
| `variants` | list | no | related entries: `{"id", "relation"}` with `relation` one of `newer`, `older`, `patched`, `same-family`, `contains`, `part-of` |
| `docs` | list of strings | no | documents that describe the piece: case documents (relative paths), the author's documentation, URLs |
| `notes` | string | no | short notes; longer ones go in `notes.md` |

### 3.6 Kinds

| `kind` | Has | Matched by |
| --- | --- | --- |
| `code` | `code.bin`, `mask`, `entries` | bytes and mask (3.8) |
| `data` | `data.bin`, a mask when parts vary | bytes and mask: fonts, pictures, tables |
| `format` | `detect.py` | the detector: structures that hold different bytes in every copy (a PT3 module, a Hrust stream) |
| `rom` | `entries` with `offset` = the ROM address, no bytes | the program's `CALL` / `JP` / `RST` targets into the ROM; `origin` is the ROM's name (`"48k"`, `"tr-dos-5.04t"`) |

### 3.7 Roles

`player`, `sfx`, `depacker`, `packer-setup`, `protection-layer`, `loader`, `sector-reader`, `interrupt`, `input`,
`paging`, `print`, `screen`, `sprite`, `font`, `picture`, `table`, `rom-call`, `game-module`, `demo-part`,
`music-data`, `stream`. A new role needs a row here first.

### 3.8 How a piece matches

| Match | Condition | Reported |
| --- | --- | --- |
| `exact` | the bytes at the place equal `code.bin` | the id, the address, `delta` = address minus `origin` |
| `masked` | every unmasked byte equal, and all `rel16` words give one delta | the same, plus each `ext16`, `var8`, `var16` value by name and each `data` range |
| `candidate` | at least half of the entry's anchors (section 4) hit in order at consistent offsets, but no full match | the id, the address, the differing offsets; a person decides whether it is a new variant |

A `masked` match must have at least 32 unmasked bytes, or it is reported as a `candidate`; short pieces match too easily.

## 4. The index

`kit/sig_index.py` reads every `sig.json` under `signatures/` and writes `index.json` and `INDEX.md`. With `--check`
it also checks:

- that each entry's `id` equals its folder;
- that `sha1` and `masked_sha1` equal the file;
- that the mask ranges lie inside the bytes and do not overlap;
- that the kinds and roles are in the lists above;
- that each `variants` id exists.

An entry is never edited only in the index.

```json
{
  "schema": 1,
  "anchor_length": 12,
  "entries": {
    "packers/hrum/3.5/depacker": {
      "kind": "code", "role": "depacker", "name": "HRUM 3.5 depacker", "length": 119,
      "sha1": "...", "masked_sha1": "...", "tags": ["hrum", "packer"], "found_in": 1
    }
  },
  "by_sha1": {"<sha1>": ["packers/hrum/3.5/depacker"]},
  "by_masked_sha1": {"<sha1>": ["packers/hrum/3.5/depacker"]},
  "anchors": {"21xxxxxxxxxxxxxxxxxxxxxx": [["packers/hrum/3.5/depacker", 17]]},
  "by_role": {"depacker": ["packers/hrum/3.5/depacker"]},
  "by_tag": {"hrum": ["packers/hrum/3.5/depacker"]},
  "formats": ["formats/music/pt3-module"]
}
```

**Anchors.** An anchor is 12 bytes from an unmasked run of the entry. The key is the 12 bytes in lower-case hex, so a
scan looks every 12-byte window of the image up in the table directly, with no hash to collide.
- The index takes up to 8 anchors an entry, spread over its length.
- It skips runs with fewer than 4 distinct byte values (fills, zero tables).
- An entry with no such run gets no anchors and is found only through `by_sha1` and `by_masked_sha1`.

**The scan.** `kit/sig_scan.py IMAGE --base ADDR [--bank N] [--out hits.json] [--ann]`:
1. It looks every window of the image up in `anchors`.
2. It groups the hits by entry and by implied start address.
3. It runs the full match of 3.8 for each group.
4. It runs every `formats` detector.

The output is a list of hits: `{"id", "address", "match", "delta", "values", "differs"}`. `--ann` writes the hits'
`entries` and `labels` as `.ann` lines with the found addresses, ready to merge into the case's annotations.

`INDEX.md` is the human view, one table per folder: name, role, length, authors, year, the programs it was found in.

## 5. Format detectors

A `format` entry's `detect.py` defines one function:

```python
def detect(image: bytes, base: int) -> list[dict]:
    """every place in image (loaded at base) that holds this format:
    [{"address": int, "length": int, "name": str, "fields": {...}}]"""
```

It reads only `image`. It imports only the standard library and `kit/kitlib.py`. It returns structure fields such as
the tune's title, its author and its pattern count, not a verdict on how likely the hit is: the structure either
checks or it does not.

## 6. Adding entries

- **A finished case** adds its modules under `programs/games/<game>/` (or `demos/`). Also:
  - each third-party piece it identified goes under its domain;
  - a copy of a piece already in the base becomes one more `found_in` item on that entry, not a new entry.

  The case's WALKTHROUGH says which entries it added.
- **A piece from outside a case** (a player from its author's release) gets `found_in` with `case: null` and the
  program's name.
- After any change: `python3 kit/sig_index.py --check`, then `python3 kit/sig_index.py`, both committed with the entry.
