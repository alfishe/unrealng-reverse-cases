# Nether Earth ZS Edition: walkthrough

How the reverse was done, step by step, and which tool or recording answered each question. Terms:
[docs/README.md](docs/README.md). Standard: [GUIDE.md](../../GUIDE.md).

The case was done in two stages by agents under one lead:

- **Stage 1** (one agent): the media, the loads of both releases, the images, the packer's format, what the game
  shares with [Nether Earth](../nether-earth/WALKTHROUGH.md) (NE). Command log: `work/stage1/NOTES.md`.
- **Stage 2** (the lead and seven part agents, 2026-11-04 / 05): every part of both disks as annotated source and
  editable resources, the '99 packer bit-exact, both SCLs built byte for byte, the documents. Each part agent's
  state and commands: `work/stage2/STATE-<part>.md`; the shared brief `work/stage2/BRIEF.md`.

The owner's rule for stage 2: one `game.ann` per release split into modules, every routine named and described, the
`.asm` generated by `kit/mkgame.py`, never NE's source plus patches; the descriptions true for this game. NE served
as a seed only: its names and descriptions were copied for the entries whose bytes are NE's, then every entry
whose bytes differ was rewritten from the code (section 2.3).

Machine for every run: unreal-ng `unreal-qt` from the worktree `scratch/wt-nezs-stage1` (offscreen, muted, own port
bases 13710-13810; the part agents 16530, 17210, 17810, 19010), each instance stopped after; the `48K-BETA128` model
from `scratch/wt-gs-tool-gaps`. `RS` below is `$UNREAL_NG/tools/verification/analysis/re_session.py`.

### 2.2 The '99 packer, bit-exact

`tools/zsdepack.py` (stage 1) unpacks; the packer had to give the original streams. The search (`work/packer/`:
`greedy.py`, `runs.py`, `stats.py`) found the author's rule: the greedy longest non-overlapping match at the nearest
offset, length 2 up; a run of at least 8 at offset 1 up to 22; literal runs of 45 once 14 or more literals come; one
pad byte at the bottom. Four blocks follow it exactly; `patches` needs one hint (`src/sfx/hints/patches.lzhints`:
two matches of length 2 at 878). `python3 tools/zspack.py check` packs all five and compares.

The block's set-up and depacker were annotated once (`src/sfx/zsblock.asm`, assembled per block with `-D` values
from `src/sfx/blocks.txt`). The 2-3 sectors of slack after each packed block first looked like leftovers; they are
the block's own unpacked image from the block length on (the author packed in place, the stream over its own
output), zero past its end: `tools/build.sh` writes them, no file is kept.

### 2.3 How each `game.ann` was written

1. `kit/mkgame.py` with the part's config cut the image into entries from the L1 windows and NE's seed names.
2. Every entry whose bytes equal NE's kept NE's name and description, re-checked against this part's recordings.
3. Every changed or new entry was read from the code and the witnessed writes and described anew (the difficulty
   routines `$A5D6` / `$A5F2`, `LoadLevelCopy`, the patches, the '99 font, the level lists).
4. The auto labels left by the kit (`l_`, `sub_`, `data_`) were named until none was left (`game99`: 114, mostly
   NE's names at the same address after a byte check).
5. `--install` writes the `.asm` only when sjasmplus gives the original bytes.

### 2.4 The resources

Each resource is an editable source with its own README ([src/res](src/res/README.md)): fonts and sprites as PNG,
the tunes as `.pt3` / `.stc`, the maps as text with previews (`tools/zs_level.py`), the texts in UTF-8, the photo as
PNG (RLE re-pack), the menu strings as text. Each part's resource tool builds the bytes and checks a round trip.

### 2.5 The disks

`tools/mkscl.py` writes an SCL from a description (`src/disk98.txt`, `src/disk99.txt`: `file`, `part`, `slack`
lines). `tools/build.sh` runs everything under a lock and ends with `cmp` against the SCL in each `orig/` zip:

```
build: NEZSED98.SCL identical to orig/NEZSED98.zip
build: NEZSED.SCL identical to orig/NEZSED.ZIP
```

## 3. The stage 1 leftovers

- **LOAD MAP's keys** (`work/stage2/game99/loadmap-menu`, the patch piece `diskmap`): Q previous, A next, SPACE
  load; the ROM's KEY-SCAN every third interrupt; 96 cursor places (`$C2C4`), names past 64 garbled (`$C263`).
  P never moved it because it is not read ([05](docs/05-controls.md), 5.5).
- **The NELEV tail** (`tools/zs_level.py` derives every field from the lists and checks all twelve): 13 bytes
  written into instruction operands: the capture point count, four list pointers, the first factory record, the
  enemy's warbases and the player's GENERAL ([3.5](docs/03-build-and-load.md)). A map is a level only.
- **The '98's LOAD NEW LEVEL** (`work/stage2/game98/key5menu`, from the menu snapshot `menu98.szx`): key 5 runs 62
  `NOP`s where NE's tape load was, then `LoadLevelCopy` copies the intro's scroller text left at `$DD00` as a map;
  the list pointers become `$2020`, the map is built from ROM bytes over the code, a `CALL $ED48` lands in it at
  frame 415 and PC `$0000` comes at 462 ([3.5](docs/03-build-and-load.md)).

## 4. The machines

### 4.1 Scorpion ZS-256

```bash
python3 $RS capture --work s99 --media $C/work/scl/z99/NEZSED.SCL --disk --model SCORPION --inputs inputs/s99.txt \
  --ranges 4000-FFFF --port-base 13810 --binary $BIN --disk-boot-frames 2
```

The same for `s98`, and the explorations `e99s`, `e98s` through `tools/livelog.py` (`work/stage2/scorpion/`): both releases autostart, load and play; the '99
prints "Computer Scorpion / Memory 256Kb / TR-DOS Ver 5.03". Its memory test gives `$5CB0` = `$83`, `$5CB1` =
`$0D`. The radar's `ЗАГРУЗИСЬ` there is the built-in map, a joke, not a fault.

### 4.2 48K + Beta 128: the '99 resets

unreal-ng gained a `48K-BETA128` model in `scratch/wt-gs-tool-gaps` during this case; its run of the '99 shows
"Computer Spectrum / Memory 56Kb / TR-DOS Ver 5.03", and about 300 frames after the second SPACE resets (PC
`$34B6-$34BB` -> `$0001` -> `$11CB`). Verified from the code: the test counts 0 pages, the one-page route
(`$62B4`) needs exactly 1, so the 128 K route runs; the 64 text sectors are read to `$C000-$FFFF`, over the game's
patched table at `$C100`; START calls `$C100`, which now holds the about text; it runs as code (`CALL PE,$A0AD`,
`RST $28`) into the ROM calculator and NEW. `r99-48` frames 5647-5664 show the same, with the Sinclair screen at
5760. The texts' "runs on 48K" is false; the '99's one-page and tape code is unreachable
([3.6](docs/03-build-and-load.md)).

### 4.3 Pentagon 128: the TR-DOS item hang is the game's

Stage 1 noted the '99 hanging when started from the Pentagon 128 menu's TR-DOS item and blamed a patched ROM. It is
the game's incompatibility with the original Pentagon ROM: its IM 1 handler at `$004A` goes through `$386E` to
`$3A42` when FLAGS bit 4 is set (as that menu item leaves it), and `$3A42` writes `$5B88`, inside the depacker every
block copies to `$5B00` and runs with interrupts on (`DepackGetBits+5`). The disk's autostart and the 48 BASIC path
leave bit 4 clear. ZS most likely tested on Scorpion or Leningrad-type machines only
([3.6](docs/03-build-and-load.md)).

## 5. The owner's questions

- **Numbered snapshots chosen with the mouse.** menu99 searched every block for a port `$xxDF` read: none. The
  menus read the keyboard (`$DDE4`); the only Kempston read is the joystick (`IN ($1F)`, `$D3AC`). LOAD MAP lists
  the `N` names without numbers; a NELEV file is a level (game99 compared the 512 bytes with the game's state:
  nothing of robots, the day or the owners is in it). The only sixteen numbered entries on the disk are a tool's
  buffer in the readme's slack. Documented in [01](docs/01-game-design.md), 1.7 and [05](docs/05-controls.md), 5.5.
- **The claims.** Checked against the code in [01, 1.10](docs/01-game-design.md), as ANE's 1.13 does.

## 7. What stays open

- The impassable places of `NEdescri`: the freeze while fire is held is real, how it would leave a cell blocked is
  not traced.
- ATM Turbo 2+: SelectPage writes `$7FF7` while the memory test uses `$FFF7`; no ATM run.
- "Let the Battle begin!" (`$676F`) is printed by nothing.
- The '99 packer's and RLE decoder's authors; the tool that left the `CONVER Commander` buffer in the readme's
  slack; the '98 robot stream's packer; where the sector leftovers of the pictures and music blocks come from.
- The tape and one-page code of the '99 (never reachable) is read from the code only, including its operand slips
  (`$62AF` writes `$C133`; the tape BC / DE).
